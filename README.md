# Data Report

Тестовое задание: обработка выгрузки заказов с маркетплейса, сверка двух источников данных и расчёт показателей по продажам.

## Возможности

- **Сверка двух источников** — сопоставление выгрузки отчёта по продажам и реестра заказов по номеру заказа, поиск расхождений (что есть только в одном файле, где отличается сумма/количество).
- **Расчёт показателей** — выручка по товару (SKU), доля возвратов, топ-5 по обороту.
- **Обращение к внешнему API** — проверка статуса заказа с ретраями (экспоненциальная задержка) и логированием.
- **Планировщик** — запуск обработки по расписанию через APScheduler.
- **Логирование** — структурированные логи в файл через Loguru.
- **CLI-интерфейс** — настройка путей и параметров через аргументы командной строки.

## Требования

- Python 3.12+
- [uv](https://docs.astral.sh/uv/) (менеджер пакетов)

## Установка

```bash
# Клонировать репозиторий
git clone https://github.com/yunusov/blagov_data_report.git
cd blagov_data_report

# Установить зависимости
uv sync
```

## Конфигурация

Создайте файл `.env` в каталоге `src/` (образец — `src/.env.example`):

```env
ORDERS_FILE=data/orders.xlsx
ORDERS_FOR_CHECK=data/Реестр заказов (для сверки).xlsx
ORDER_STATUS_API_URL=https://api.example.com/orders/{order_id}/status
scheduler_interval=60
```

| Переменная | Описание | По умолчанию |
|------------|----------|--------------|
| `ORDERS_FILE` | Путь к файлу с заказами (xlsx) | `orders.xlsx` |
| `ORDERS_FOR_CHECK` | Путь к реестру заказов для сверки (xlsx) | `Реестр заказов (для сверки).xlsx` |
| `ORDER_STATUS_API_URL` | URL API для проверки статуса заказа (плейсхолдер `{order_id}`) | — |
| `scheduler_interval` | Интервал планировщика в секундах (0 — запуск без планировщика) | `60` |

| Аргумент | Описание |

## Результаты

После запуска в каталоге `reports/` создаются файлы:

- `reconciliation.txt` — отчёт о сверке двух источников: сколько совпало, сколько расхождений, номера заказов только в одном из файлов, детали расхождений по сумме/количеству.
- `indicators.txt` — показатели по выгрузке: выручка по товару, доля возвратов, топ-5 по обороту.
- `last_run.txt` — метка времени последнего успешного запуска (для healthcheck).

Логи пишутся в `logs/app.log` (ротация 10 МБ, хранение 1 месяц).

## Как это работает

1. **`load_orders()`** — читает Excel-файл с заказами, обрабатывает ошибки (пустой файл, отсутствие файла, битый файл).
2. **`calc_revenue_by_sku()`** — считает выручку по каждому SKU (`price × qty`), исключая отменённые заказы.
3. **`report_two_sources()`** — объединяет выгрузку и реестр по `order_id`, находит расхождения и записывает отчёт.
4. **`report_indicators()`** — считает выручку по товару, долю возвратов и топ-5 по обороту.
5. **`get_order_status()`** — обращается к API для проверки статуса заказа, с ретраями (3 попытки, экспоненциальная задержка 1→2→4 сек) и логированием.
6. **`Scheduler`** — запускает `process_data()` по расписанию через APScheduler.

## Мониторинг в проде

### 1. Успешность выполнения

- **Статус завершения** — утилита завершилась успешно или с ошибкой? В логах ищите `process_data завершён` или `Ошибка в process_data`.
- **Время выполнения** — резкое замедление сигнализирует о проблемах (большой файл, медленный API).
- **Количество обработанных заказов** — совпадает ли с ожидаемым.

### 2. Сверка двух источников

- **Количество расхождений** — `совпало / только в выгрузке / только в реестре / расхождения по значениям`. Резкий рост — сигнал проблемы в данных.
- **Новые расхождения** — заказы, которые раньше сходились, а теперь нет (регрессия).

### 3. API (внешний сервис)

- **Количество ретраев** — частые ретраи = нестабильный API.
- **Коды ошибок** — `Timeout`, `ConnectionError`, `HTTPError` (особенно 5xx).
- **Время ответа API** — медленный API замедляет всю обработку.

### 4. Данные

- **Пустые/битые файлы** — `EmptyDataError`, `BadZipFile` — файл не пришёл или повреждён.
- **Отсутствующие колонки** — `ValueError` из `calc_revenue_by_sku` — изменилась структура выгрузки.
- **Аномалии** — отрицательные цены, нулевое количество, дубликаты `order_id`.

### 5. Инфраструктура

- **Диск** — логи (`logs/`) и отчёты (`reports/`) растут. Ротация логов уже настроена (10 МБ), но диск стоит контролировать.
- **Память/CPU** — при больших файлах pandas может потреблять много памяти.
- **Процесс жив** — если используется планировщик, проверять, что процесс не упал (healthcheck по `reports/last_run.txt`).

### 6. Бизнес-метрики

- **Выручка по товару** — резкое изменение может указывать на ошибку в расчёте или в данных.
- **Доля возвратов** — рост доли возвратов — бизнес-сигнал.
- **Топ-5 по обороту** — изменился ли состав топ-5.

## Запуск по расписанию (cron / schtasks)

Вместо встроенного планировщика можно использовать системный:

**Linux (cron):**
```cron
0 * * * * cd /path/to/blagov_data_report && uv run python -m src.main --interval 0
```

**Windows (schtasks):**
```bat
schtasks /create /tn "BlagovReport" /tr "cd /d J:\dev\python\blagov_data_report && uv run python -m src.main --interval 0" /sc hourly
```
